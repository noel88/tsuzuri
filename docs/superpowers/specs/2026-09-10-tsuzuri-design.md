# Tsuzuri (綴り) — 설계 문서

**작성일:** 2026-09-10
**대상 기기:** KING JIM pomera DM250 (Debian 모드)
**상태:** 설계 확정, 구현 전

---

## 1. 무엇을 만드는가

한↔일 **양방향 번역 작문 드릴**. 번역기가 아니다. 프로그램이 한쪽 언어로 문장을 제시하면 사용자가 반대 언어로 작문하고, 그 작문에 대해 피드백을 받는다.

- `ko2ja` — 한국어 제시문 → 일본어로 작문
- `ja2ko` — 일본어 제시문 → 한국어로 작문

핵심 성질은 **평소에는 네트워크 없이 돌아간다**는 것이다. 포메라를 들고 나가서 오프라인으로 계속 연습할 수 있어야 하고, 네트워크는 문제를 받아올 때와 첨삭을 수령할 때만 쓴다.

## 2. 확인된 환경 제약

전부 조사로 확인한 사실이며, 설계의 근거다.

| 항목 | 값 | 설계 영향 |
|---|---|---|
| SoC | Rockchip RK3128, 쿼드 Cortex-A7 | **32비트 ARMv7 (armhf)**. arm64 아님 |
| 클럭 | 기본 816MHz (개조 시 1.3GHz) | 시작 시간·분석 속도의 상한 |
| RAM | 1GB | 사전 로딩이 실질적 제약 |
| OS | Debian 11 bullseye | |
| 콘솔 | fbterm (일본어 표시·입력) | ANSI 지원 범위 불확실 → 풀스크린 TUI 회피 |
| GUI | xfce4 + mozc (`startx`) | 포인팅 디바이스 없음 → 콘솔 우선 |
| 화면 | 7" 1024x600 | |
| 네트워크 | Wi-Fi 동작 (brcmfmac43430) | |
| 공유 영역 | SD카드 vfat — 순정 포메라 OS와 공유 | 복습 노트를 순정 모드에서 읽는 경로 |
| 부팅 | 좌Alt+우Shift+전원일 때만 Debian, SD 빼면 순정 복귀 | |

### 이 제약이 배제한 것

- **CTranslate2 / Argos Translate** — 지원 아키텍처가 x86-64와 AArch64. armhf는 대상 밖이라 오프라인 NMT의 가장 현실적인 경로가 막힌다.
- **llama.cpp 로컬 첨삭** — armv7 빌드 자체는 가능하나 RAM 1GB에서 Q4 0.5B급이 상한이고, Cortex-A7 816MHz에서는 실용 속도가 안 나온다. 0.5B 모델의 일본어 첨삭 품질도 신뢰 대상이 아니다.
- **Claude Code 직접 실행** — 요구사항이 4GB+ RAM, x64 또는 ARM64. 배포 플랫폼 목록에 `linux-arm`(32비트)이 없어 바이너리가 존재하지 않는다. "느리지만 돌아간다"가 성립하지 않는다.

## 3. 범위

### 하는 것

- 레벨·주제를 골라 문제 팩을 온라인으로 생성·저장
- 오프라인 출제 → 작문 입력 → 형태소 분석 기반 자동 분석 → 참조 번역 제시
- 첨삭 요청을 오프라인 큐에 적재, 온라인 시 일괄 수령
- 복습 노트를 순정 포메라 모드에서 읽을 수 있는 `.txt`로 출력

### 하지 않는 것

- **점수·정오 판정** (§5.4에 근거)
- 오프라인 기계 번역
- 로컬 LLM 추론
- 음성·사전 검색 전용 모드
- SRS(간격반복)는 M5로 유보 — 실사용 후 필요성이 확인되면 추가

## 4. 아키텍처

### 4.1 명령 구조

```
tsuzuri init      레벨·주제 선택 → 팩 생성            [온라인]
tsuzuri           출제 → 작문 → 분석                  [오프라인]
tsuzuri sync      큐 flush + 팩 보충                  [온라인]
tsuzuri export    복습 노트를 .txt로 출력             [오프라인]
```

네트워크를 쓰는 지점은 `init`과 `sync` 둘뿐이다. 이 경계를 코드 구조에서도 유지한다 — 분석 엔진은 HTTP 클라이언트를 알지 못한다.

### 4.2 저장소 레이아웃

SD카드의 vfat 공유 영역에 둔다. 순정 포메라 모드에서도 보이는 위치다.

```
/mnt/sd/tsuzuri/
  config.toml          API 키, 기본 레벨·주제, 모델
  packs/*.jsonl        문제 팩
  attempts.jsonl       답안 + 자동 분석 결과 (append-only)
  queue.jsonl          첨삭 대기 (append-only)
  feedback.jsonl       수령한 첨삭 (append-only)
  review/*.txt         순정 포메라 모드용 복습 노트
```

### 4.3 저장 형식: JSON Lines (SQLite 아님)

세 가지 이유로 결정했다.

1. **포메라는 덮으면 그냥 꺼지는 기계다.** append-only JSONL은 최악의 경우 마지막 줄만 손상되고 복구가 자명하다. vfat 위의 SQLite는 락·저널 처리가 취약하다.
2. Go에서 cgo 없이 SQLite를 쓰려면 `modernc.org/sqlite`인데 armhf 동작을 별도로 검증해야 한다. 이 규모에서 치를 값이 아니다.
3. **데이터가 작다.** 문장 수천 개, 답안 수천 개. 시작 시 전량을 메모리에 올려도 무방하다.

읽기는 시작 시 전량 로드 후 인메모리 인덱스, 쓰기는 append + `fsync`.

### 4.4 문제 팩 스키마

```jsonc
{
  "id": "p047",
  "dir": "ko2ja",              // ko2ja | ja2ko
  "level": "N3",
  "topic": "일상",
  "prompt": "어제 처음 간 카페가 생각보다 조용해서 오래 앉아 있었다.",
  "reference": "昨日初めて行ったカフェが思ったより静かで、長く座っていた。",
  "key_points": ["初めて", "思ったより", "〜ていた"],
  "traps": ["「静かくて」는 な형용사 활용 오류"],
  "style": "plain"             // plain(보통체) | polite(정중체)
}
```

**`key_points`와 `traps`가 이 설계의 핵심이다.** 팩을 생성할 때 문장쌍만 받는 게 아니라 **채점에 쓸 근거까지 함께 받아 저장한다.** 그 결과 오프라인에서 LLM 없이도 근거 있는 분석이 가능하다. 온라인 호출 한 번으로 수백 문제어치의 채점 지능을 미리 사오는 구조다.

### 4.5 답안·큐·첨삭 스키마

```jsonc
// attempts.jsonl
{"id":"a012","pack_id":"p047","at":"2026-09-10T14:22:03+09:00",
 "answer":"昨日初めて行ったカフェは静かくて、ずっと座ってました。",
 "analysis":{"covered":["初めて","〜ていた"],"missing":["思ったより"],
             "unknown_tokens":["静かく"],"style_mismatch":true,
             "ref_only":["思う","長い"],"ans_only":["ずっと"],
             "len_ratio":0.82}}

// queue.jsonl
{"attempt_id":"a012","priority":false,"at":"2026-09-10T14:22:05+09:00"}

// feedback.jsonl
{"attempt_id":"a012","at":"2026-09-11T09:03:11+09:00",
 "corrected":"昨日初めて行ったカフェは思ったより静かで、長く座っていた。",
 "notes":[{"span":"静かくて","why":"「静か」는 な형용사라 て형은 「静かで」","level":"error"},
          {"span":"ずっと","why":"틀리지 않지만 「長く」가 원문의 시간 길이에 더 가깝다","level":"nuance"}],
 "overall":"활용 오류 하나를 빼면 의미는 정확히 전달됩니다."}
```

## 5. 오프라인 분석 엔진

### 5.1 형태소 분석기

**kagome** (`github.com/ikawaha/kagome/v2`). pure Go로 cgo 의존이 없어 armhf 크로스컴파일이 한 번에 된다. 이것이 Go를 선택한 결정적 이유다.

사전은 **사용자가 작문한 언어** 기준으로 로드한다. 제시문 언어가 아니다.

| 방향 | 작문 언어 | 사전 |
|---|---|---|
| `ko2ja` | 일본어 | `kagome-dict/ipa` (IPADIC) |
| `ja2ko` | 한국어 | `kagome-dict-ko` (mecab-ko-dic, **experimental**) |

**한 팩은 한 방향으로 고정하고, 한 드릴 세션도 한 방향만 다룬다.** `init`이 방향을 물어 팩 단위로 분리 저장하고, `tsuzuri` 실행 시 방향을 고른다. 그 결과 사전은 항상 하나만 상주한다 — 두 사전을 동시에 올리지 않는 것이 R1 대응의 전제다.

### 5.2 검사 항목

1. **핵심 표현 커버리지** — `key_points` 각 항목이 답안에 있는지 확인. 형태소의 **기본형**으로 비교하므로 활용이 달라도 매칭된다 (`思わなかった` → `思う`).
2. **미지어(UNKNOWN) 탐지** — 사전에 없는 토큰. 오타·조어·활용 오류의 강한 신호다. `静かくて` 같은 형태가 여기 걸린다.
3. **문체 일관성** — 일본어는 です·ます체 ↔ だ·である체 혼용, 한국어는 해요체 ↔ 한다체 혼용. 문제의 `style` 필드와 대조한다.
4. **참조 대비 어휘 차이** — 내용어(명사·동사·형용사)만 집합 비교. 참조에만 있으면 "빠뜨림", 답안에만 있으면 "덧붙임"으로 표시.
5. **길이·문장 수** — 참조 대비 비율이 임계를 벗어나면 표시.

### 5.3 하지 못하는 것

- **조사 오용 판정** (`は`/`が`, `に`/`で`) — 문맥 의존이라 규칙으로 판정 불가. `traps`에 걸린 항목만 힌트로 노출한다.
- **자연스러움·뉘앙스**
- **어순 적절성**
- **참조와 다르지만 동등하게 옳은 답의 구분**

### 5.4 점수를 매기지 않는다 (핵심 원칙)

§5.3의 마지막 항목이 이유다. 번역은 정답이 여럿인데 참조는 하나뿐이다. 참조와 다르다고 감점하면 **맞는 답을 틀렸다고 가르치게 된다.**

따라서 오프라인 분석은 판정하지 않고 **짚어주기까지만** 한다. 화면의 `✗`와 `⚠`는 오답 표시가 아니라 **확인 요청**이다. 판정과 뉘앙스 평가는 LLM 첨삭의 몫이다.

이 원칙은 구현 전반에 적용된다 — 점수 필드, 정답률, 정오 카운터를 데이터 모델에 두지 않는다.

## 6. 입력과 화면

### 6.1 풀스크린 TUI를 쓰지 않는다

두 가지 이유다.

1. fbterm은 프레임버퍼 터미널이라 ANSI 지원 범위가 불확실하다.
2. **더 중요한 이유** — 풀스크린 TUI는 raw mode로 키를 한 글자씩 읽는데, 그러면 mozc IME의 입력 경로가 깨질 위험이 있다. 일본어 입력이 안 되면 앱이 성립하지 않으므로 감수할 리스크가 아니다.

### 6.2 라인 기반 설계

- 답 입력은 **canonical mode의 일반 줄 입력** — IME가 터미널의 정상 입력 경로를 그대로 쓴다
- 명령은 짧은 문자 + Enter (`f`↵ = 첨삭 요청)
- `:e` 입력 시 `$EDITOR`(vim/nano) 호출 — 긴 답안용. 포메라 사용 맥락에 오히려 자연스럽다

### 6.3 화면 양식 — PC통신(하이텔) 스타일

레이아웃은 1990년대 PC통신 게시판 양식을 따른다. 취향만의 선택이 아니다 —
하이텔은 애초에 **번호를 쳐서 이동**하는 방식인데, §6.1에서 mozc IME 때문에
raw mode를 포기했으므로 우리 조작도 "타이핑 + Enter"다. 같은 제약에서 나온
같은 답이라 잘 맞는다.

**초기화면** — 좌측 번호 메뉴, 우측 자료 목록, 하단 명령어 안내

```
╔══════════════════════════════════════════════════════════════════════════╗
║ 綴 / T·S·U·Z·U·R·I                                  한↔일 번역 작문 드릴 ║
╚══════════════════════════════════════════════════════════════════════════╝

      팩 2개 · 남은 문제 59 · 첨삭 큐 12건 · 오프라인

  1. 드릴 시작                    ┌──────────┐
  ──────────────────────          │ 자 료 실 │
  2. 이어하기                     └──────────┘
  ──────────────────────            41. ko2ja  N3 일상                47
  3. 팩 받기                        42. ja2ko  N2 뉴스                12
  ──────────────────────
  4. 설정                         ┌───────┐
  ──────────────────────          │ 복 습 │
                                  └───────┘
                                    51. 첨삭 대기                     12
                                    52. 받은 첨삭                     34

 ──────────────────────────────────────────────────────────────────────────
 주요명령(드릴 D, 복습 R)  이동(번호)  종료(X)
 선택(도움말[H]) >>
```

**드릴 화면** — 트리 사이드바를 상시로 두지 않는다. 사이드바가 20칸 남짓을
먹으면 좁은 폰트에서 일본어 문장이 줄바꿈되고, 그러면 「나 vs 참조」 대조가
무너진다. 메뉴는 초기화면에만 두고 드릴에서는 본문이 화면을 온전히 쓴다.

```
┌──────────────────────────────────────────────────────────────────────────┐
│ p047   ko2ja   N3   일상                                           12/47 │
└──────────────────────────────────────────────────────────────────────────┘

  어제 처음 간 카페가 생각보다 조용해서 오래 앉아 있었다.

  나  : 昨日初めて行ったカフェは静かくて、ずっと座ってました。
  참조: 昨日初めて行ったカフェが思ったより静かで、長く座っていた。

  ────────────────────────────────────────────────────────────────────────
  ✓ 「初めて」   ✓ 「ていた」   ✗ 「思ったより」 빠짐
  ⚠ 「静かく」   사전에 없는 형태
  ⚠ 문체        답안 정중체 / 문제 보통체
  ────────────────────────────────────────────────────────────────────────

 ──────────────────────────────────────────────────────────────────────────
 주요명령(다음 ⏎, 첨삭 F, 다시 R)  메뉴(M)  종료(X)
 선택 >>
```

`✓` `✗` `⚠`는 오답 표시가 아니라 확인 요청이다 (§5.4). 지적할 것이 없는
줄은 아예 그리지 않는다 — 다 맞은 답이면 `✓` 한 줄과 참조만 남아 조용하다.

### 6.4 폭 계산과 정렬

- **모든 폭 계산은 표시폭 기준이다.** 한글·한자·가나는 터미널에서 두 칸을
  차지하므로 rune 개수로 세면 CJK가 섞이는 순간 테두리가 어긋난다.
  `ui.Width()`가 East Asian Wide/Fullwidth 범위를 판정한다.
- **터미널 폭은 `COLUMNS`에서 읽는다.** fbterm 폰트 크기에 따라 칸 수가
  달라지므로 하드코딩하지 않는다. 없거나 이상하면 76칸으로 본다.
- **블록은 화면 가운데, 본문은 블록 안에서 왼쪽 정렬.** 각 줄을 개별로
  가운데 정렬하면 「나」와 「참조」의 시작 위치가 어긋나 대조가 안 된다.

### 6.5 색을 쓰지 않는다

DM250이 7" 1024x600 백라이트 TFT인 것은 확인했으나, 사양표에 표시색 항목이
없어 컬러 여부를 확정하지 못했다. 어느 쪽이든 **흑백에서 온전히 읽히도록**
만든다. 박스 드로잉은 색과 무관하게 동작한다.

**M0에서 확인할 것:** `✓ ✗ ⚠ ╔ ═ ┌ │ ─` 글리프가 fbterm 폰트에 있는가.
`✓✗⚠`가 두부(□)로 뜨면 `+ - !`로 폴백한다. 박스 문자는 대부분 있다.

## 7. 온라인 부분

### 7.1 API

Anthropic 공식 Go SDK (`github.com/anthropics/anthropic-sdk-go`)를 사용한다. pure Go라 크로스컴파일 제약이 없다.

- 기본 모델: `claude-opus-5` (`config.toml`에서 변경 가능)
- 팩 생성은 **구조화 출력**(`output_config.format`)으로 스키마를 강제해 파싱 실패를 없앤다
- 긴 응답은 스트리밍 + `.get_final_message()` 계열 헬퍼로 HTTP 타임아웃을 피한다
- 적응형 사고(`thinking: {type: "adaptive"}`) 사용

### 7.2 `init` — 팩 생성

레벨·주제·방향(`ko2ja` 또는 `ja2ko`)·개수를 받아 방향별 팩 파일로 §4.4 스키마의 배열을 생성한다. 프롬프트는 다음을 명시한다.

- 제시문은 학습자가 실제로 쓸 법한 자연스러운 문장일 것
- `reference`는 유일한 정답이 아니라 **모범 예시 하나**임을 전제로 작성
- `key_points`는 그 레벨에서 연습 가치가 있는 표현으로 3개 내외
- `traps`는 한국어 화자가 이 문장에서 실제로 저지르는 오류

### 7.3 `sync` — 첨삭 수령

`queue.jsonl`을 읽어 배치로 처리한다. 각 항목에 제시문·참조·내 답안·오프라인 분석 결과를 함께 보내 첨삭의 근거로 삼는다. 결과는 `feedback.jsonl`에 append.

**첨삭 프롬프트의 원칙:** 참조와 다르다는 이유로 지적하지 말 것. 실제 오류(`error`)와 더 나은 선택(`nuance`)을 구분해 표시할 것. §5.4의 원칙을 온라인 쪽에서도 유지한다.

### 7.4 비용

200문제 생성 + 월 100건 첨삭 기준 추정치다.

| 모델 | 팩 200문제 | 월 100건 첨삭 | 월 합계 |
|---|---|---|---|
| Haiku 4.5 | $0.20 | ~$0.33 | ~$0.5 |
| Sonnet 5 | $0.40 | ~$0.66 | ~$1 |
| Opus 5 | $1.00 | ~$1.65 | ~$2.7 |

첨삭은 큐에 전부 적재한다. 이 비용에서 선별할 이유가 없다. `[f]`는 우선 처리 표시로만 쓴다.

### 7.5 보안

API 키가 `config.toml`에 평문으로 들어가고, 그 위치는 **SD카드의 vfat 영역**이다. 기기나 SD를 분실하면 노출된다.

**대응:** 이 앱 전용 키를 발급하고 사용량 제한을 건다. 다른 용도의 키를 재사용하지 않는다. 이 사실을 `init` 시점에 사용자에게 한 번 안내한다.

### 7.6 시계 문제

포메라는 Debian을 가끔만 띄우므로 시스템 시각이 밀려 있을 수 있다. 시각이 어긋나면 **TLS 인증서 검증이 실패해 API 호출이 통째로 막히며, 원인 파악이 어려운 부류의 에러**가 난다.

`init`과 `sync` 시작 시 시스템 시각을 확인하고, 의심스러우면 사용자에게 시각 동기화를 안내한다.

## 8. 빌드와 배포

맥에서 크로스컴파일한다.

```bash
GOOS=linux GOARCH=arm GOARM=7 CGO_ENABLED=0 go build -o tsuzuri
```

산출물을 SD카드에 복사하거나 Tailscale로 `scp`한다. **포메라에는 빌드 툴체인이 필요 없다.**

주의: kagome 사전은 Go 모듈로 바이너리에 임베드되므로 산출물이 상당히 커진다. 용량 자체는 SD카드에서 문제가 아니지만 **로딩 시간에 영향을 준다** (§9의 R1).

## 9. 리스크와 검증 계획

구현 전에 M0 스파이크로 확인한다. 여기서 결과가 나쁘면 설계를 수정한다.

| ID | 리스크 | 확인 방법 | 실패 시 대응 |
|---|---|---|---|
| R1 | **kagome 사전 로딩 시간·메모리 미측정** — SD I/O + 816MHz에서 몇 초 걸릴지 모름 | 실기에서 사전 로드 후 시작 시각·RSS 측정 | 방향별로 바이너리 분리, 또는 사전을 외부 파일로 분리해 지연 로드 |
| R2 | **한글 콘솔 입력 미검증** — DM250 이미지는 일본어 전제. fbterm에서 한글 입력이 되는지 불명. `ja2ko` 방향이 여기 걸림 | fbterm에서 한글 입력기 설치·시도 | ① 콘솔용 한글 입력기 추가 ② `ja2ko`만 X11에서 실행 ③ 로마자 입력 허용 |
| R3 | **ko-dic이 kagome에서 experimental** — 한국어 분석 품질 불명 | 한국어 문장 샘플로 분석 결과 육안 확인 | `ja2ko` 방향의 검사 항목을 1·4·5번(사전 의존이 낮은 것)으로 축소 |
| R4 | 크로스컴파일 바이너리의 실기 동작 | hello world 실행 | GOARM 값 조정, 정적 링크 확인 |
| R5 | HTTPS/TLS 및 API 도달성 | 실기에서 API 호출 1회 | §7.6 시각 동기화, CA 인증서 갱신 |
| R6 | **fbterm 폰트의 글리프 지원 미확인** — `✓ ✗ ⚠` 및 박스 문자가 두부로 뜰 수 있음 | 실기 콘솔에 해당 문자 출력 | `+ - !` 등 ASCII로 폴백 |

## 10. 마일스톤

### M0 — 스파이크 (버리는 코드)

§9의 R1~R5를 순서대로 확인한다. **산출물은 코드가 아니라 판단 근거다.** 여기서 만든 것은 전부 폐기한다.

### M1 — 오프라인 루프 (네트워크 없음)

손으로 작성한 팩 10문제로 출제 → 입력 → 분석 → 저장까지 완결시킨다. **API 코드가 한 줄도 없다.** 앱의 핵심 가치를 네트워크 없이 먼저 검증하는 단계다.

### M2 — `init` (온라인)

레벨·주제 선택 UI, 팩 생성, 저장.

### M3 — 첨삭 큐 + `sync` (온라인)

큐 적재, 배치 처리, 첨삭 표시.

### M4 — `export` (오프라인)

순정 포메라 모드에서 읽을 복습 노트 `.txt` 생성.

### M5 — SRS·진도 (유보)

실사용 후 필요성이 확인되면 착수한다. 지금은 만들지 않는다.

## 11. 결정 기록

이후에 "왜 이렇게 했나"를 묻게 될 항목들이다.

| 결정 | 이유 |
|---|---|
| Go + kagome | armhf에서 cgo 없이 크로스컴파일 한 방. 포메라에 툴체인 불필요. 일본어·한국어 형태소 분석을 한 라이브러리로 |
| 오프라인 우선 + 하이브리드 | 포메라의 존재 이유가 오프라인 몰입. 단 LLM 첨삭은 armhf에서 로컬 불가 |
| 채점 근거 선생성 (`key_points`/`traps`) | 온라인 한 번으로 수백 문제어치의 오프라인 채점 지능을 확보 |
| JSON Lines | 급작스러운 전원 차단에 강함. cgo 회피. 데이터 규모가 작음 |
| 점수 없음 | 참조는 유일한 정답이 아니다. 잘못된 자동 점수는 학습을 해친다 |
| 풀스크린 TUI 회피 | raw mode가 mozc IME를 깨뜨릴 위험. 일본어 입력은 타협 불가 |
| API 사용 (구독 아님) | 구독 자격증명으로 API를 호출하는 지원 경로가 없음. 비용이 월 1~2천원 수준이라 포메라 자립성을 사는 값으로 타당 |
| M1을 네트워크 없이 완결 | 핵심 가치를 API 코드 없이 먼저 검증 |
